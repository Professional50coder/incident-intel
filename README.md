# Incident Intelligence

Triage tool for fixed-camera video: upload a clip, get a score for every moment, a short list of flagged segments to review with plain-language explanations, and an exportable incident report. Under the hood is an unsupervised PyTorch autoencoder benchmarked honestly against two baselines on UCSD Ped2.

**Live demo:** LIVE_URL_PLACEHOLDER

## What it is for, and what it is not

It narrows hours of footage from one fixed camera to a handful of "most unusual moments" you can watch, confirm or dismiss, and export. Its edge is the workflow around the model: a false-alarm budget instead of a magic threshold, event segments instead of frame scores, a review loop, and reports. See [`docs/market-research.md`](docs/market-research.md) for the prior-art scan behind that positioning.

It is **not** a certified security product. The model is weak-to-moderate (frame-level AUC 0.674 on Ped2, below published results of roughly 90%) and was trained on one scene. A flag means "this moment looks unlike the rest of the clip", never "an incident happened". See [Limitations](#limitations).

## Quickstart

Zero setup with Docker (sample clips are inside the image):

```bash
docker build -t incident-intel . && docker run -p 7860:7860 incident-intel
# landing page at http://localhost:7860/ , analysis app at http://localhost:7860/app
```

Or with Python 3.10+:

```bash
git clone https://github.com/Professional50coder/incident-intel && cd incident-intel
python -m venv venv && source venv/bin/activate        # Windows: venv\Scripts\activate
pip install torch torchvision --index-url https://download.pytorch.org/whl/cpu
pip install -r requirements.txt && pip install -e .
uvicorn incident_intel.api.main:app                     # landing http://localhost:8000/ , app /app
```

### First run

1. Open `/app` (the landing page's **Try a sample** button goes there) and press **Analyse this clip** on a sample (for example *cart crossing*).
2. Read the plain-language summary, then the timeline: red marks are flagged moments. Segments are ranked, each with a low/medium/high confidence label (a heuristic from how far and how long the clip departs from its own baseline, not a calibrated probability). Click the chart to jump the video there.
3. Review each flagged segment: **Watch**, then **Confirm incident** or **False alarm**.
4. Tune the **alert budget** slider (1-20% of frames) to trade missed events against false alarms; segments update instantly.
5. Export **JSON / CSV / Markdown**, print to PDF, or copy the report link.
6. Upload your own clip (mp4, avi, mov, mkv, webm; default limit 30 MB and about 6000 decoded frames).

Flagging modes:

| Mode | Rule | Use when |
|---|---|---|
| Relative to this clip (default) | Top *budget* fraction of the clip AND at least 5 robust sigma (median/MAD) above the clip median | Any scene. Bounds alarms per clip |
| Ped2 calibrated | Score above 0.00047 (Youden's-J point on the Ped2 test ROC) | Only the UCSD Ped2 walkway |

The sample clips (`samples/`) are **synthetic** (generated by `scripts/make_samples.py`), because Ped2 footage is not redistributable here. They demonstrate the workflow, not accuracy. What I measured on them: the cart in *cart crossing* (about 0:09.6-0:10.8) and in *runner and cart* (about 0:16.7-0:17.9) are flagged; the small runner at 0:06-0:08 is **missed**; *quiet walkway* has no flags. The Ped2-calibrated threshold is not meaningful for these clips (the page warns when most frames exceed it).

## Benchmark: what was measured

**Frame-level AUC-ROC, UCSD Ped2 official test set, 64x64 grayscale, micro-averaged** (all test frames pooled into one ROC; no per-video AUC and no per-clip score normalisation were computed):

| Candidate | AUC-ROC |
|---|---|
| Frame-diff baseline (no learning) | **0.7093** |
| MobileNetV2 embedding k-NN (frozen) | 0.6879 |
| Conv autoencoder, 150 epochs (served) | 0.6742 |
| Conv autoencoder, 20 epochs | 0.6451 |

These are well below the ~90-95% the literature reports on Ped2. The simplest baseline wins; the autoencoder is served anyway for reasons in [Why the autoencoder](#why-the-autoencoder-despite-a-lower-score).

**Audit status (October 2026).** The three AUC values above match the committed run files (`runs/phase1-*.json`), enforced by `tests/test_readme_claims.py`. The Ped2 dataset is **not** in this repository or on the machine used for this audit, so I did **not** regenerate any of these numbers, and I could not re-derive the threshold's TPR/FPR (0.38 / 0.10) or the 20-epoch figure (its run file was not kept). Treat those as recorded, unverified claims. The committed checkpoint loads and produces scores (tested), so the served model exists; whether it is exactly the 150-epoch model behind 0.6742 is recorded, not proven.

## Reproduce the model comparison

```bash
# download UCSD Ped2 (http://www.svcl.ucsd.edu/projects/anomaly/dataset.html) into data/raw/
python -m incident_intel.experiments.phase1_model_selection \
    data/raw/UCSD_Anomaly_Dataset.v1p2/UCSDped2 --epochs 150
```

This rebuilds the checksummed manifest ([`data/manifests/ucsdped2-v1.json`](data/manifests/ucsdped2-v1.json)), runs all three candidates, writes one JSON per candidate to [`runs/`](runs) (git commit, config, metric) and overwrites `checkpoints/autoencoder.pt`. The default is `--epochs 20`; the served checkpoint used 150. The k-NN candidate downloads MobileNetV2 weights through torchvision.

Provenance of the numbers: `runs/phase1-frame-diff.json` (0.7093), `runs/phase1-embedding-knn.json` (0.6879), `runs/phase1-autoencoder.json` (0.6742, 150 epochs). The 20-epoch figure (0.6451) comes from the write-up in [`docs/model-selection/phase-1.md`](docs/model-selection/phase-1.md); its run file was not kept. The dataset is not in the repo, so these numbers are the recorded ones and were not regenerated for this README; the test suite (47 tests) was run and passes.

## Model selection

| Candidate | How it scores | Learnable? | AUC-ROC |
|---|---|---|---|
| Frame-diff | mean absolute pixel distance from the mean normal frame | no | 0.7093 |
| Embedding k-NN | mean distance to the 5 nearest normal-frame MobileNetV2 embeddings | no (frozen encoder) | 0.6879 |
| Conv autoencoder | mean squared reconstruction error | yes | 0.6742 (150 ep), 0.6451 (20 ep) |

All three are fit on normal training frames only and scored on the same test frames, using [`compute_auc_roc`](src/incident_intel/eval/metrics.py) (scikit-learn). The autoencoder has three stride-2 conv layers (1 to 16 to 32 to 64 channels), a mirrored transposed-conv decoder with a sigmoid, and trains with Adam (lr 1e-3, batch 32, MSE).

### Why the autoencoder despite a lower score

- Frame-diff has no parameters, so training ablations, synthetic-anomaly augmentation and temporal modeling (roadmap phases 2, 3, 5) cannot build on it.
- The gap is 0.035 AUC (0.709 vs 0.674), modest rather than decisive.
- The reconstruction-error map is a natural source for a per-region evidence view that frame-diff would need extra work to match.

Full reasoning: [`docs/model-selection/phase-1.md`](docs/model-selection/phase-1.md).

### Operating threshold

`ANOMALY_THRESHOLD = 0.00047` was chosen as the Youden's-J point on the autoencoder's ROC curve over the Ped2 test set, at roughly TPR 0.38 and FPR 0.10 (figures from the write-up, not re-derived here). The threshold is tuned on the same data it is reported on.

## Limitations

- **Accuracy is modest.** AUC 0.674 for the served model; at the threshold about 38% of anomalous frames are caught and about 10% of normal frames flagged. A flag is a signal, not a verdict.
- **Resolution.** Frames are downsampled to 64x64 grayscale (from Ped2's 240x360) to fit a 4 GB laptop GPU. This is a likely contributor to the gap with published results, though no ablation here isolates it.
- **No motion.** Every candidate scores single frames independently, while Ped2 anomalies (bikes, carts) are defined by motion. A temporal model is planned, not built.
- **Selection and reporting share data.** Ped2 has only 12 test clips, so model choice, threshold and reported AUC all use the same test set. Numbers are optimistic for unseen data.
- **Single run**, no seeds or confidence intervals recorded.
- **Single scene.** The checkpoint has only seen the Ped2 walkway; other scenes need their own normal-only training footage.
- **Privacy and security.** No accounts. Uploads are size/type limited, streamed to a temp file and deleted after scoring; only file name and scores are stored. History is scoped to a random per-browser id, but report ids work as share links, and a free host's disk is ephemeral (history may reset on restart). The budget heuristic has only been checked on synthetic clips.
- **Sampling.** Every 5th frame is scored, so events shorter than about 0.4 s at 12 fps can be missed (the small synthetic runner was).

## How a request flows

1. The dashboard posts the file as multipart form data to `POST /analyze`.
2. The API writes it to a temporary file and opens it with OpenCV.
3. Every 5th frame (`EVERY_NTH_FRAME`) is converted to grayscale, resized to 64x64 (`FRAME_SIZE` in [`config.py`](src/incident_intel/config.py)) and scaled to [0, 1]. The temporary file is deleted. No readable frames gives a `400`.
4. The autoencoder (loaded lazily from `checkpoints/autoencoder.pt`, on CPU) scores each frame by reconstruction error; frames above the threshold are flagged.
5. The result is stored as JSON in the SQLite `incidents` table and returned.

## Design decisions

| Decision | Why | Trade-off |
|---|---|---|
| Serve the autoencoder, not the top-scoring frame-diff | Only candidate with learnable capacity for later phases | Gives up 0.035 AUC today |
| 64x64 grayscale | Trains within 4 GB VRAM | Loses small-object detail |
| Evaluate on the full official Ped2 test set | Only 12 test clips; matches how the literature reports | Selection and reporting reuse the same data |
| Checksummed manifest per dataset version | Any run traces to exact frames | One extra step per dataset change |
| Local JSON run logs, no MLflow or W&B | No third-party telemetry | No experiment UI yet |
| `create_app()` with injectable scorer and DB path | Tests need no checkpoint | Slightly more wiring |
| CPU-only Docker image | Small model, no GPU needed to serve | Retraining needs a separate GPU setup |
| Backend off Vercel serverless | Package size, cold starts, ephemeral disk | Two deploy targets |
| Checkpoint committed (190 KB) | API works after clone | Binary in git history (force-added past a `checkpoints/*` ignore rule) |

## Deploying

The dashboard and backend deploy separately, to different kinds of host. See
[`docs/deployment.md`](docs/deployment.md) for why the backend specifically shouldn't go on
Vercel serverless, and what to use instead (the repo's [`Dockerfile`](Dockerfile) builds a
portable CPU-only image for it).

**Dashboard → Vercel.** Set `dashboard` as the project root and set
`NEXT_PUBLIC_API_URL` to the backend's public URL.

**Backend → any container host** (a VPS with Docker Compose, Railway, Render or Fly.io):

```bash
docker build -t incident-intel-api .
docker run -d -p 8000:8000 \
  -e DASHBOARD_ORIGIN=https://your-dashboard.vercel.app \
  -v $(pwd)/data:/app/data \
  incident-intel-api
```

- The `-v` mount keeps `data/incident_intel.db` across restarts. Without it, history resets on
  every deploy.
- `DASHBOARD_ORIGIN` must match the deployed dashboard's URL exactly, or the browser blocks the
  API calls as cross-origin.
- Once the backend has a public URL, set it as `NEXT_PUBLIC_API_URL` in Vercel and redeploy the
  dashboard.
